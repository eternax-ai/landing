The 100-Key Vault: one block, no Bitcoin fork

Bitcoin is not post-quantum secure today, and the fix in the protocol is years away. We propose a method, One-Time Vaulting, that makes Bitcoin custody post-quantum secure at rest and quantum-resilient in flight on the Bitcoin mainnet today: no fork, no miner deals, no change to wherever your keys already live, one ordinary transaction. Bitcoin will become post-quantum on its own schedule, once the protocol upgrades and the economy migrates; this method is for the years in between.

By Paarrthhh Birla, Co-Founder, EternaX Labs · Dariia Porechna, Co-Founder and Cryptography Lead, EternaX Labs

The One-Time 100-Key Vault is a Bitcoin custody method, built from the standard P2WSH output and 100 fresh ECDSA keys that all must sign, each address spent exactly once. It is post-quantum secure at rest, because only a SHA-256 hash is visible, and quantum-resilient in flight, because an attacker must derive all 100 private keys inside one Bitcoin block interval. Using the estimate in Google Quantum AI’s 2026 paper Securing Elliptic Curve Cryptocurrencies against Quantum Vulnerabilities: Resource Estimates and Mitigations, about nine minutes per key on a first-generation fast-clock quantum computer, an attacker with seven such machines succeeds about once in 730,000 spends, with twenty about 1% of the time, and with a hundred about 41%. On published expert surveys and vendor roadmaps, the method holds below one in a million per spend through about 2032 and below 1% through about 2035, which covers the estimated seven-year window for Bitcoin to adopt native post-quantum signatures. It requires no change to Bitcoin, no relationship with miners, and no change to existing hardware security modules; a spend costs about 2,800 virtual bytes (2,759 measured on mainnet for one input and one output). The method is called One-Time Vaulting, written OTV; implemented here by EternaX Labs in October 2026.

1. The problem not priced in

If you have heard that Bitcoin is not post-quantum secure and that nothing can be done about it until the protocol changes, the first half is true and the second is not. This piece shows a way to hold and move bitcoin that a quantum computer cannot touch at rest and can only race in flight, built entirely from what Bitcoin already does, and proves it with an ordinary mainnet transaction. First, the problem as it actually is.

Bitcoin ownership is a public key. Whoever can turn a public key into its private key owns the coins, and a sufficiently large quantum computer running Shor's algorithm does exactly that. Nothing else about Bitcoin changes when it arrives; only the signatures stop meaning anything. Two things make this sharper than the usual story: secp256k1's 256-bit keys need a smaller quantum computer than RSA-2048, and there is no undo. A bank that loses a wire to fraud has recourse; a bitcoin moved by a forged signature is gone.

The question that matters is not "when will a quantum computer exist" but "when it does, which of my coins can it reach, and how fast". Google Quantum AI's March 2026 whitepaper, co-authored with the Ethereum Foundation and Stanford, gives the first careful answer, and it splits the problem into two attacks that are not alike.

At rest: coins whose key is already visible

If a public key is sitting on the blockchain, an attacker can read it today and work on it for as long as they like. Three kinds of bitcoin are in this state: the original pay-to-public-key outputs (about 1.7 million BTC, including Satoshi's), every Taproot address, because Taproot writes the public key into the output, and every reused address, because the first spend revealed the key. Google counts roughly 6.9 million BTC in this condition; BIP-361's authors put it at more than 34% of supply. For these coins the only cure is to move them before a quantum computer exists.

In flight: every other coin, for about ten minutes

The remaining two thirds of bitcoin sit behind a hash. The chain shows a fingerprint of the key, not the key, and a quantum computer cannot invert a hash in any useful time. That protection holds until the owner spends. To spend, the owner must reveal the public key so the network can check the signature, and from that moment until the transaction is buried in a block, the key is public and the race is on.

Google's whitepaper is the first to put a number on that race. Its optimised circuits need either 1,200 logical qubits and 90 million Toffoli gates or 1,450 and 70 million, fitting in fewer than half a million physical superconducting qubits, and take about 23 or 18 minutes per key. Half of Shor's algorithm depends only on the curve, so a machine can be "primed" in advance; from that state Google estimates roughly 12 or 9 minutes from seeing a public key to holding its private key, and simplifies to "about 9 minutes" for the first generation of fast machines.

Bitcoin blocks arrive on average every ten minutes, but randomly: the wait is exponentially distributed, so a nine-minute quantum attacker beats the next block about 41% of the time. The number, per Google, assumes a single key, no network congestion, and an attacker who then outbids you for block space. The last assumption is now the network's default: since Bitcoin Core 28, any unconfirmed transaction can be replaced by a conflicting one that pays a higher fee.

Google paper notes only fast-clock machines, superconducting, photonic or silicon-spin, can run this race; ion-trap and neutral-atom machines are 2-3 orders of magnitude slower and more likely attack coins at rest long before coins in flight. And the first such machine may not announce itself: early quantum computers "may first be detected on the blockchain rather than announced."

The same paper warns against the opposite failure mode: unscientific resource estimates are themselves a form of attack on the system. So every number in this article is cited to a primary source and scope.

2. Bitcoin can't fix it this year

The proper fix is a post-quantum signature scheme in Bitcoin's consensus rules, so that a coin can be locked to a key no quantum computer can derive.

Currently, Bitcoin's scripting language can verify exactly two kinds of signature, ECDSA and Schnorr, both on the same vulnerable curve. It has no opcode for SLH-DSA, ML-DSA or any other post-quantum scheme, no way to express one with existing opcodes, and the only post-quantum primitive it offers at all is the hash function. Adding a new signature scheme means a soft fork. BIP-360, "Pay to Merkle Root", was merged into the BIPs repository as a draft in February 2026; it removes Taproot's exposed key path but defers post-quantum signature opcodes to a future proposal. BIP-361, the proposal to retire legacy signatures on a schedule, is also currently a draft.

User adoption timelines are an another unknown. A BIP-360 co-author has estimated that even on an optimistic path, with consensus reached and no setbacks, migration takes about seven years: two and a half years of review and testing, half a year to activation, and roughly five years for most of the economy to move. A bank holding bitcoin today cannot plan on the protocol solving the problem for it.

So the constraint on a method that works now is severe: no change to consensus or relay policy, no relationship with miners, no new software for nodes, nothing new for the device that holds the keys to learn. The only post-quantum material Bitcoin offers is the hash. The only lever it offers on the in-flight race is how much work the attacker must do and how long they have.

The chart above is the shape of the problem. The lower band is how long Bitcoin needs; the upper band is how long a method built from today's Bitcoin can hold. Everything that follows is built for the span between those two dates, and built to be left behind at the end of it.

3. The One-Time 100-Key Vault

A 100-Key Vault is a standard Bitcoin P2WSH address built from 100 fresh keys that all have to sign, used exactly once, with the decision to spend made by a hash-based signature that no quantum computer can forge. The mechanism is One-Time Vaulting; written generally it is OTV(N), and OTV(100) is the instance this piece is about, because 100 is the most keys Bitcoin Core's default policy relays in a single input.

In plain words: you generate 100 brand-new keys, in a hardware security module for a bank or on an offline computer for an individual, build a script that says "all 100 must sign", and put bitcoin into the address that is the hash of that script. On chain that is all anyone sees, for as long as the coins sit there. When it is time to move them, whoever governs the vault approves one exact transaction with a hash-based signature that lives off-chain; only then does the signing device produce the 100 signatures, and the transaction goes out exactly as any other: Bitcoin Core nodes relay it, pools on Core's policy mine it, and it confirms in the next block that takes it. Change goes into a new vault with 100 new keys in the same transaction. The 100 keys that signed are deleted and never used again.

That is the whole method. Nothing in it is new to Bitcoin, and two of its parts are not new at all. Never reusing an address has been Bitcoin's own advice since 2010. Using several keys as a quantum defence was proposed by Holmes and Chen at the University of Surrey in 2021, up to the 20 keys that Bitcoin's multisig opcode allows, with the observation that it multiplies the attacker's required capacity but can be attacked in parallel. What has not been done is to take the number to the ceiling: 100 keys needs a different construction than the one everyone uses, it sits exactly at the limits Bitcoin Core relays, and nobody had built it, spent it on mainnet, put a hash-based approval gate around it, or quantified it against a dated fleet of quantum machines. That combination is what we call One-Time Vaulting, and the 100-Key Vault is its first instance. This is the first description of it.

Locked by hash at rest

A resting vault is safer than a single hashed address, for a reason that is itself post-quantum. There are exactly two ways to move its coins: produce 100 valid ECDSA signatures, which needs the 100 public keys, hidden behind a SHA-256 hash of the script that a quantum computer cannot invert; or persuade the device that holds the keys to sign, which needs the off-chain lock to open first: an approval signed with SLH-DSA, the hash-based scheme NIST standardised as FIPS 205, which a quantum computer cannot forge. For an institution that approval is a quorum of officers; for an individual it is one hash-based key on a token they hold. Both locks rest on hash functions. Shor's algorithm is irrelevant to either. The curve matters only during the minutes of the spend itself, which is why that moment gets the next four sections.

Nothing in the method requires an institution. Hardware security modules and officer quorums are how a bank runs it; the construction itself is a script, a rule about reuse, and a hash-based approval, and it scales down. The same vault at 20 keys uses Bitcoin's ordinary multisig opcode and can be built by any wallet software that can construct a custom witness script; 100 keys is the reserve-grade setting. The number is a dial. What does not change with the dial is the discipline: every address used once, every spend approved by a signature a quantum computer cannot forge, change into a fresh vault.

A 100-Key Vault shows the chain nothing until it spends, and when it spends, it shows everything at once and only once.

The script

The vault is a pay-to-witness-script-hash output. Its witness script is a chain of 100 signature checks:

<pubkey_1>   OP_CHECKSIGVERIFY
<pubkey_2>   OP_CHECKSIGVERIFY
   …
<pubkey_99>  OP_CHECKSIGVERIFY
<pubkey_100> OP_CHECKSIG

One hundred 33-byte keys and one hundred opcodes come to 3,500 bytes. Bitcoin Core's relay policy allows a witness script of up to 3,600 bytes and up to 100 witness items per input; its source code notes that these limits are "adequate for multisignatures up to n-of-100 using OP_CHECKSIG". So 100 is not a number chosen for effect. It is the largest vault a single input can hold and still be relayed under Bitcoin Core's default policy. Bitcoin Knots is stricter: its default -maxscriptsize of 1,650 bytes counts the whole witness, which caps the chain at 15 keys, so Knots nodes, and the OCEAN pool that runs them, neither relay nor mine a 100-key spend; Core nodes relay it and other pools mine it. Our mainnet spend, one input to one output, weighed 2,759 virtual bytes, roughly 20 times an ordinary payment; with a change output it is about 2,800.

Why not the familiar OP_CHECKMULTISIG? It is capped at 20 keys by consensus, and chaining five of them pushes the witness past the 100-item limit. The chain of single checks is both larger and standard.

The chain sees only a hash until the spend

4. A theft needs all 100 keys before the next block

Here is the whole in-flight argument in one sentence: the attacker must derive every one of the 100 private keys from the 100 public keys, in the time between your broadcast and the next block, and then win a fee auction. Everything else is arithmetic.

Google's whitepaper states the two facts that govern that arithmetic, and we quote both because they cut both ways: "The cost of quantum attacks on multi-signature transactions, such as P2WSH, increases linearly with the number of signatures required. However, these attacks parallelize trivially, so an attacker with a sufficient number of CRQCs can achieve the probability shown in Figure 6." And: "for scripts that require a large number m of signatures, on-spend attacks by an attacker with a small number of CRQCs are made more difficult by the need to derive a large number of private keys in the ten minutes average block interval."

So the honest model is this. Take an attacker with M primed machines, each needing about 9 minutes per key. To break N keys they need ⌈N/M⌉ rounds of 9 minutes, and they succeed if the next block takes longer than that: probability e−0.9·⌈N/M⌉. Table B shows what that gives.

The guarantee, in the words we are prepared to defend

At rest, a 100-Key Vault is behind two hash-based locks: no elliptic-curve public key exists on-chain or off-chain outside the signing device, so a quantum computer has no target, and the device will not sign until an SLH-DSA approval of the exact transaction exists, which a quantum computer cannot forge. Security at rest rests on the preimage resistance of SHA-256 and the security of SLH-DSA (FIPS 205). In flight, theft requires an adversary to derive all N secp256k1 private keys between broadcast and confirmation and to win the resulting fee auction; against fewer than roughly N/15 primed fast-clock quantum computers (fewer still if batch optimisations are engineered) the chance is below one in a million per spend, and against N or more it is 41% or worse. This is a resource bound on the attacker, not a cryptographic hardness bound, and it is offered as a defence for the migration window, not as post-quantum security. Not covered: coins left in exposed outputs, a leaked signed transaction, collusion of all signing parties, a hash-function break, or an attacker who can also reorganise the chain.

5. A thief must pass seven gates

"Hard" is not one argument. It is a sequence of gates an attacker has to pass in order, each with its own number, its own source, and a date for when it weakens. Together they are the case for 100.

Gate 1. Only fast-clock machines can race

Google's paper separates quantum platforms by how fast they run a single operation. Superconducting, photonic and silicon-spin machines are fast-clock. Trapped ions and neutral atoms, which hold today's records for logical qubits, are "about two to three orders of magnitude slower": a key that takes nine minutes on fast hardware takes fifteen hours to six days on slow. That threatens coins whose keys are already visible, and not a spend that confirms in minutes. Half the quantum industry is not in this race. Weakens if: slow-clock platforms find magic-state techniques suited to their hardware, which Google calls plausible and nobody has shown.

Gate 2. A fleet, not a machine

Each key is a separate run of Shor's algorithm. One first-generation machine working through 100 keys needs about fifteen hours, during which roughly ninety blocks go by. For the single-key odds of 41% the attacker needs 100 machines running at once; for one in a hundred, twenty; for one in a million, seven. On the published expert surveys and vendor roadmaps we assess a coordinated fleet of seven fast-clock machines as unlikely before about 2032 and no better than one in eight by 2035.

Say the limit out loud: adding keys multiplies the attacker's hardware, not the difficulty of the mathematics. Going from one key to a hundred adds about log2(100) ≈ 6.6 bits of work, and nobody calls 6.6 bits a security parameter. What those bits buy is time, during which the machines that could use them are few, expensive, and owned by governments and hyperscalers. Against a handful, an OTV(100) spend is safe to better than one in a million; against a hundred it is a coin flip. The method is a bet about how many such machines exist before Bitcoin adopts post-quantum signatures, and the bet should be made with the chart in front of you.

Table B in section 4 is kind to the vault in one way an attacker would not be. Litinski's 2023 work shows a quantum computer can derive several keys in one execution by reusing its initial state, nine per run in Google's description, which Google's headline numbers exclude. An attacker building a machine for vault spends, where all 100 keys arrive together, would use it. The effect is that 100 keys become roughly a dozen batch runs, each longer and needing more qubits than a single-key run; on that assumption the one-in-a-million line holds against one machine rather than six, and a dozen batching machines would reach roughly a 13% shot. Treat the right-hand columns of Table B as the optimistic case.

Weakens as: fast-clock programmes go from one-off machines to production, and as per-key time falls, because every halving of key time halves the fleet required.

Gate 3. Primed, idle, and waiting for you

Half of Shor's algorithm depends only on the curve and can be precomputed; the machine then sits "in this primed state until a public key is available," in Google's words. A one-time key that confirms before it is derived is worthless a minute later, so there is nothing to stockpile. The fleet has to be primed and idle at the exact moment you broadcast, which could be any day, and while it waits it is not working through the roughly 6.9 million bitcoin already exposed on chain, at about three keys per machine-hour. A rational attacker drains that pool first; your spend is at the bottom of the queue until it is gone. Weakens when: exposed coins have been migrated or stolen and fleets have idle capacity, the late 2030s on any current projection.

Gate 4. Beat a block that arrives at random

This is the only gate with a probability, and the rest of the piece rests on it. Blocks arrive every ten minutes on average but at random, so the chance the next one is still pending after t minutes is e−t/10: 41% at nine minutes, 13.5% at twenty, 0.25% at an hour. An attacker with M machines at nine minutes a key needs 9 × ⌈100/M⌉ minutes. Seven machines need 135 minutes, which the next block outlasts about once in 730,000 spends; ten machines, once in 8,000; twenty, about 1%. The tables are generous in one more way: a machine must re-prime between keys, so every round after the first really costs closer to eighteen minutes than nine. Weakens as: per-key time falls or the window is stretched (the heat map below).

Gate 5. Outbid the fee

Deriving the keys gives the attacker a signature, not the coins. Their replacement must displace yours in every miner's mempool, and since Bitcoin Core 29.0 the rule is uniform: a replacement must pay a strictly higher fee, plus an increment for its own size. A custodian signs a ladder of higher-fee versions of the same transaction before destroying the keys, so the attacker has to climb past every rung. Google notes this can become a "scorched earth" auction in which the fee eats the asset; with the odds at gate 4, it is an auction the custodian can afford to lose once in a very long time. Weakens if: never, mechanically; it is policy Bitcoin Core nodes already run.

Gate 6. The loot has to exceed the cost

Each attempt costs the attacker 100 key-derivations of quantum machine time, whatever the outcome, plus any flooding bought to stretch the window; the expected gain is the slice's value times the odds at gate 4. With a value cap per spend the attack is irrational whenever cap × odds is less than 100 × cost-per-key. At any plausible first-generation cost per key, tens of thousands of dollars of amortised capital alone, a seven-machine attacker would need a single spend in the hundreds of billions to break even. The cap starts to bind only against fleets the size of the vault. Weakens as: machine time gets cheap; review the cap whenever a credible cost estimate halves.

Gate 7. Six blocks and it is over

After confirmation the keys are dead unless the attacker can orphan the block that holds your spend. Google describes that attack, a bribe to miners to abandon the block while the keys are derived, and states that reversal cost "grow[s] exponentially in the number of blocks." Natural single-block reorganisations happen a handful of times a year; a six-block one has never been bought. A six-confirmation rule makes post-confirmation theft a majority-hashrate problem, which is a different attack on a different thing. Weakens if: hashrate centralises, which has nothing to do with quantum computing.

Large fleets and mempool flooding are the two weak points

Two gates are honest weak points: a large enough fleet walks through gate 2, and an attacker who floods the mempool stretches gate 4. Holmes and Chen worked out the hybrid in 2021: flood for about two blocks and lean on the difficulty, and Bitcoin's effective window becomes about 31 minutes. Faster keys need a new generation of hardware

Could the attacker just build a faster machine? The constraint is not the qubits but the loop around them: every layer of a fault-tolerant computation waits for a classical computer to decode the errors and feed back. Google assumes that loop takes 10 microseconds; the best published figure, from Google's own Willow processor, is 63, and that decoder does not yet feed back into the logical circuit at all. The trade that does exist is Google's: doubling the qubits roughly doubles the speed. A machine ten times faster than the first therefore needs either a decode loop ten times faster than anything built, or ten machines' worth of qubits. Either is a generation of hardware. Weakens as: decoder latency approaches 10 µs, which we would expect leading groups to reach around the turn of the decade.

The defence holds to about 2035

Through about 2032, the chance that any one OTV(100) spend is stolen in flight is below one in a million with high confidence, because that requires a fleet of seven or more fast-clock machines, which we assess at five percent or less to exist by then. Through about 2035 it stays below one percent, which requires twenty such machines, or ten plus a sustained stretching of the window. From about 2038 the construction should no longer be relied on by itself. Those dates are our synthesis of the Global Risk Institute's 2025 expert survey, the Metaculus forecast for factoring RSA-2048, and the IBM and PsiQuantum roadmaps; they are estimates, reviewed every year against the signals in section 8. That window is the medium term this method is built for, and it is wider than the window Bitcoin needs to adopt post-quantum signatures.

A vault spend costs about twenty times an ordinary payment

One input, two outputs, the payment and a fresh vault for the change: about 2,800 virtual bytes, roughly twenty times an ordinary payment (our mainnet spend, one input to one output, weighed 2,759). At 2 satoshis per virtual byte that is 5,600 satoshis, about $4.50; at 10 sat/vB, 28,000 satoshis, about $22; at 50 sat/vB, seen only in congested periods, 140,000 satoshis, about $112. All at $80,000 per bitcoin, where it closed on 26–27 October 2026, against positions typically eight or nine figures. OTV(20) for operational wallets costs about a quarter, roughly $5.40 at 10 sat/vB. There is no other cost: ordinary key-generation and signing calls, a standard transaction, nothing paid to anyone but the miner. A custodian with Bitcoin signing in place can pilot on signet in weeks and on mainnet the quarter after.

7. Most objections are true, and the design accounts for them

We wrote this section before publishing by asking what the sharpest reviewers in three communities, Bitcoin Core, quantum computing, and bank custody, would say first. Here is what they would say, and what is true in it.

"Isn't 100 keys just 100 machines?"

Yes. Google says it plainly: the attacks "parallelize trivially", which is why every curve in Figure 3 reaches 41%, and spare machines push past it. What the objection misses is the other half of the same paragraph: against an attacker with a small number of machines, which is what the first generation will be, deriving 100 keys in ten minutes is exactly the obstacle. The method is a bet on fleet size over a window of years, and the fleet sizes are in a table rather than a slogan: a seven-machine fleet is unlikely before about 2032, twenty before the mid-2030s, and a hundred, or one machine a hundred times faster, is a late-2030s proposition on anything published today.

"What about one bigger machine?"

Also true. Google notes that doubling the qubits roughly doubles the speed, and that eleven primed machines working one key together get a 6.5× speedup. A machine a hundred times the first would do 100 keys serially inside a block; it is also a hundred times harder to build than one that does not yet exist. The question for a risk committee is not "can this be beaten in principle" but "by whom, when, and at what cost per spend", and section 8 gives the signals that say when to stop relying on it.

"Attacks always get better."

They do, and the trend is the strongest argument for treating this as a bridge. Between 2017 and 2026 the estimated cost of breaking one secp256k1 key fell by orders of magnitude on every axis: roughly 1,800× fewer Toffoli gates from Roetteler et al. to Google, about 20× fewer physical qubits from Litinski's photonic estimate to Google's superconducting one, and about 10× less spacetime volume between the two most recent. A defence worth 6.6 bits can be erased by one good paper. That is why the migration plan in section 8 is part of the method, not an afterthought.

"This isn't post-quantum cryptography."

In flight, correct, which is why we say resilient and not resistant. At rest it is: a SHA-256 commitment and an SLH-DSA approval gate are post-quantum cryptography in the ordinary sense. The in-flight security of a 100-Key Vault still rests on ECDSA over secp256k1, which NIST's draft transition timeline (IR 8547) lists as disallowed after 2035 and CNSA 2.0 phases out for national security systems by 2033. Neither binds a commercial custodian, but no auditor will call ECDSA post-quantum, and we do not ask them to. What the method gives you is the only post-quantum property Bitcoin can express today, the hash at rest, a hash-based governance layer around the spend, and a quantified work factor in the one window where Bitcoin cannot yet help you.

"Bitcoin never verifies your hash-based approvals."

True by construction. Bitcoin checks 100 ECDSA signatures and nothing else; the SLH-DSA approval is enforced off-chain, by the software that decides whether the keys are asked to sign. Its job is not to make the chain post-quantum but to ensure the one moment of exposure happens only when the right people have agreed to the exact transaction, so the attacker's only route is the race and not the approval. Who can trigger the signatures is answered two objections below; section 8 shows how the same approval trail becomes the migration record.

"The window isn't really ten minutes."

Correct. Blocks are random, the mempool can be flooded, and the Surrey paper's hybrid attack puts Bitcoin's effective window at about 31 minutes if an attacker pays for it. The heat map in section 5 shows what that does: against seven machines the odds go from one in 730,000 to one in 2,400; against twenty, from 1% to 22%. So a vault spend is never broadcast into a congested mempool and always pays a next-block fee with margin, which is cheap and removes most of the lever. And the window argument only bites against fleets of ten or more fast-clock machines, the same fleet the first objection already needs: it makes an existing large attacker more dangerous, not a new one.

"Wouldn't they just go after the exposed coins first?"

Yes, and that is a guard, not a gap. About 6.9 million bitcoin already sit with keys visible on chain, attackable at leisure at roughly three keys per machine-hour, with no race and no deadline. The first owner of a quantum computer has years of that work waiting. A vault spend, by contrast, requires the whole fleet idle and primed at the exact second of broadcast for a capped slice behind a hundred keys. It is the worst target on the list, and it stays that way for as long as the list exists.

"What about a reorg?"

Google describes it: when a high-value key first appears in a block, an attacker can pay miners to orphan that block while the quantum computer works on the key, then collect in the replacement. It is real, and it means the window does not end at the first confirmation. It also requires buying a chain reorganisation, which is expensive, public, and grows exponentially harder with every block; natural ones are a handful of single-block events a year. The method's response is a rule: a vault spend is final at six confirmations, and the value in any one spend is capped so that buying a reorganisation is never worth it.

"At rest, you're just a SegWit address."

Yes. Every unreused bc1q address hides its key behind a hash, and Google's paper recommends exactly that hygiene as the first mitigation. The at-rest property is Bitcoin's, not ours. What the method adds is enforcement: a vault address cannot be reused, cannot be exposed through a shared master key, and cannot be spent without the hash-based approval, and when it is spent, the attacker faces 100 keys rather than one. Hygiene that is enforced by construction is worth more than hygiene that is recommended.

Two further objections come from custody rather than quantum computing, and they are the ones a bank's reviewer asks first.

"Who can trigger the 100 signatures?"

Ordinary signing devices, HSMs included, sign whatever they are asked to sign; they cannot see a hash-based approval. If one program can ask all 100 keys to sign, that program is the custody, and anyone who compromises it needs no quantum computer. The method's answer is that no single system may hold that power: the 100 keys are spread across independent signing systems under separate control, including one the asset owner runs, and each checks the hash-based approvals against the exact transaction before signing its share. Stealing means breaching all of them at once, the standard every multi-party custody system is held to. The operating rules that make it concrete are a custodian's implementation, published separately.

"What if one of the 100 keys is lost?"

A script that needs all 100 keys has no mercy on its own: one failed device and the coins are gone. The answer uses the same hash that hides the main path: the witness script can carry a second spending path, for a separate recovery quorum, that opens only after a fixed date. Like the main path, it is hidden only while the vault is unspent. A P2WSH spend reveals the whole witness script, unused branch included, so every ordinary spend also publishes the recovery keys, and they are retired with the vault. That is why the lock must be a date, an absolute timelock, with each vault rolled into a fresh one before it arrives: a relative delay would already have run out on any vault older than the delay, and an attacker racing an ordinary spend could take the coins through the recovery path, which has far fewer keys. The branch also costs one main key, 99 instead of 100, because choosing a path takes one of the 100 witness items Bitcoin Core relays, and the recovery quorum fits in the remaining script space only up to about three keys. If a key is lost, the custodian waits for the date and moves the coins to a fresh vault; that recovery spend races with only the recovery quorum's keys, so it is for emergencies. It is the timelock machinery that has protected cold storage since 2016, placed behind a one-time hash.

8. One spend moves the vault to post-quantum outputs

Everything above is designed to be temporary. When Bitcoin activates native post-quantum outputs, a 100-Key Vault migrates in one ordinary spend: the 100 keys sign a transaction whose output is a post-quantum address, the keys are revealed once, the coins are then locked by a signature scheme no quantum computer can forge, and no curve key has ever been visible at rest at any point in the coins' history. That last property is the one that matters. Coins that spent the waiting years in a Taproot address, or in a reused address, carry an exposed key into the migration and have to run the race one last time with the whole world watching; coins that waited in a One-Time Vault run it on their own terms, in a transaction of the custodian's choosing, with 100 keys.

Two more things the method leaves behind for that day. The hash-based approval trail, kept off-chain, is a timestamped record of every spend decision that no quantum computer can have forged, which is the kind of evidence a BIP-361-style recovery phase or a regulator will want. And the discipline itself carries over: post-quantum signatures are large, and the value caps and recovery paths a custodian learns now are what it will run then, with different keys.

Five signals mean it is time to move

A bridge is only honest if you say when to get off it. The dates in the chart in section 2 are reviewed every year against the indicators in section 5. Any one of the following signals means the in-flight bet is no longer worth making, and cold reserves should move to the strongest construction available at the time, whether that is native post-quantum outputs or a hash-locked spend path that has by then become standard:

  • A publicly demonstrated fault-tolerant machine passes roughly a thousand logical qubits on a fast-clock platform.
  • A logical error rate below one in a hundred million is demonstrated at scale.
  • A published estimate cuts the cost of breaking a 256-bit curve key by another factor of five.
  • Any unexplained theft from an address with an exposed key.
  • Native post-quantum outputs activate on Bitcoin.

The bridge is the point. It is what lets a custodian say, truthfully, that its bitcoin was never exposed at rest and that it never had to choose between acting now and waiting for the protocol.

10. Questions people ask

Answered in the first sentence, then expanded, with a link to the section that shows the evidence. These are the questions as people type them; each has its own anchor for citing.

Is Bitcoin quantum safe?

No. Every bitcoin is secured by an ECDSA or Schnorr signature on the secp256k1 curve, which Shor's algorithm breaks on a large enough quantum computer. About a third of all bitcoin already has its public key visible on chain and can be attacked at leisure once such a machine exists; the rest is safe only until it is spent. No such machine exists today. Google Quantum AI's 2026 estimate is under half a million physical qubits and about nine minutes per key on a first-generation fast machine. See section 1.

Will quantum computers break Bitcoin?

They can break the signatures that prove ownership, not Bitcoin itself. A large enough quantum computer running Shor’s algorithm can derive a private key from any public key it can see; blocks, mining and the hash functions are unaffected. What that means in practice depends on whether your public key is visible: about a third of bitcoin is exposed today, the rest only during a spend. No such machine exists yet; Google Quantum AI’s 2026 estimate puts the first one at under half a million physical qubits. See section 1.

How can I protect my bitcoin from quantum computers?

Three things, in order. Move any coins in Taproot, pay-to-public-key or reused addresses to fresh hashed addresses now, while no quantum computer exists. Hold reserves in one-time, all-keys-sign addresses, 100 keys if your custodian can build them and 20 if not, and spend each address once. Decide in advance what will make you migrate to native post-quantum outputs when Bitcoin has them. The first step is free apart from a transaction fee; the second is the method in this piece; the third is section 8.

How much bitcoin is vulnerable to a quantum attack today?

About 6.9 million BTC, roughly a third of supply, by Google Quantum AI’s 2026 count; BIP-361’s authors put it at more than 34%. That is the bitcoin whose public key is already visible on chain: about 1.7 million BTC in early pay-to-public-key outputs, every Taproot address, and every reused address. The remaining two thirds are exposed only while a spend is unconfirmed. See Figure 1.

Are Satoshi’s coins at risk from quantum computers?

Yes, and they are the clearest case. Satoshi-era coins sit in pay-to-public-key outputs, which put the public key directly on chain, so a sufficiently large quantum computer could derive the private keys at leisure and move them. Nothing in Bitcoin as it stands can prevent that; it is why proposals such as BIP-361 discuss what to do about legacy outputs. The 100-Key Vault addresses coins that are moved into it; it cannot protect coins that stay where they are.

Can Bitcoin be made post-quantum secure without a fork?

At rest, yes, today: a coin behind a never-revealed hash has no public key for a quantum computer to attack, and the 100-Key Vault adds a hash-based approval gate so the decision to spend cannot be forged either. In flight, not fully: Bitcoin cannot verify a post-quantum signature without a soft fork, so the best no-fork method makes the spend quantum-resilient rather than quantum-resistant, by requiring an attacker to break 100 keys inside one block. The vault does the first completely and the second with a measured, dated work factor. See section 3.

What is the 100-Key Vault?

A standard Bitcoin address built from 100 fresh keys that all have to sign, used exactly once, with spends approved by a hash-based (SLH-DSA) quorum off chain. On chain it is a single SHA-256 hash until it spends; when it spends, all 100 keys appear at once and are never used again. It is the first instance of a method we call One-Time Vaulting, written OTV(100). See section 3.

What is One-Time Vaulting?

Holding bitcoin behind N fresh keys that all sign, spending each address exactly once, rolling change into a fresh address in the same transaction, and gating every spend with a hash-based approval quorum. It combines Bitcoin's own advice (never reuse an address), a 2021 academic proposal (multiple keys as a quantum defence), and a construction that reaches the 100-key relay limit. Written generally as OTV(N). See section 3.

What is the difference between quantum-resilient and quantum-resistant?

Quantum-resistant, or post-quantum, cryptography is unbroken by any known quantum algorithm; SLH-DSA and ML-DSA are examples. Quantum-resilient means a defence withstands a quantum attacker within stated limits of machines and time, rather than being immune. The 100-Key Vault is post-quantum secure at rest and quantum-resilient in flight; we use the words precisely so that a regulator or auditor reading them gets exactly what we mean.

What is an on-spend attack on Bitcoin?

An attack during the minutes between a transaction being broadcast and being confirmed in a block, when the spender's public key is visible to the whole network. A quantum computer that can derive the private key in that window can broadcast a competing transaction with a higher fee and steal the coins. Google's 2026 estimate gives a first-generation machine about a 41% chance of beating one block for a single key. Against 100 keys it needs 100 such machines for the same odds. See section 4.

What is Shor’s algorithm and why does it matter for Bitcoin?

A quantum algorithm, published in 1994, that solves the discrete-logarithm and factoring problems in polynomial time. Bitcoin’s ECDSA and Schnorr signatures rest on the discrete logarithm over the secp256k1 curve being hard, so a quantum computer large enough to run Shor against a 256-bit key can derive any private key whose public key it can see. Google Quantum AI’s 2026 estimate is about 1,200 to 1,450 logical qubits and 70 to 90 million Toffoli gates per key.

What did Google's 2026 paper actually say about breaking Bitcoin in 9 minutes?

That its optimised Shor circuits need about 1,200 to 1,450 logical qubits and 70 to 90 million Toffoli gates, fitting in under half a million physical superconducting qubits; that a full run takes about 18 to 23 minutes per key; and that because half the computation can be done before the key is known, a primed machine needs about 9 to 12 minutes from seeing a public key to holding the private key. It also said attacks on multisig outputs grow linearly with the number of keys and parallelise across machines. See section 1.

How long until a quantum computer can break Bitcoin?

Nobody knows, and the honest answers are probabilities. The Global Risk Institute's 2025 survey of 26 experts put a machine able to break RSA-2048 within a day at 28 to 49% likely within ten years and 51 to 70% within fifteen. The Metaculus community forecast for the same event has a median around 2034. Google set its own internal post-quantum migration deadline at 2029. None of these is a date; all of them say the window is this decade or the next.

What is Q-Day?

The day a cryptographically relevant quantum computer exists: one able to break the public-key cryptography in use today, including Bitcoin’s secp256k1 signatures. Nobody knows the date. The Global Risk Institute’s 2025 survey of 26 experts put a machine able to break RSA-2048 within a day at 28 to 49% likely within ten years; the Metaculus community median is around 2034; Google set its own migration deadline at 2029. Google also warns the first such machine may be detected on the blockchain before it is announced.

How many keys can a Bitcoin multisig have?

The familiar OP_CHECKMULTISIG opcode allows at most 20 keys. A chain of single OP_CHECKSIGVERIFY checks is not limited by that opcode and, under Bitcoin Core's relay rules of 3,600 bytes of script and 100 witness items per input, allows 100 keys in one input. Up to 201 keys are valid by consensus, but anything above 100 is non-standard and has to be handed to a miner directly. Spreading keys over several inputs adds nothing: each input falls to its own keys.

Why 100 keys and not 20 or 1,000?

100 is the most keys a single Bitcoin input will relay under Bitcoin Core's standard policy, so it is Bitcoin's own number, not ours. 20 is what the multisig opcode allows and is a reasonable setting for high-frequency operational wallets. More than 100 cannot be relayed in one input, and splitting a vault across inputs adds no protection: an attacker who breaks one input's keys takes that input. See section 3.

Does the 100-Key Vault require a soft fork or any change to Bitcoin?

No. It uses pay-to-witness-script-hash outputs, OP_CHECKSIGVERIFY and ordinary ECDSA, all consensus rules since 2017, in a script that Bitcoin Core's default policy relays and any miner can mine. No miner relationship, no special relay, no new software for anyone else. Bitcoin Knots' stricter default refuses it, so Knots nodes and the OCEAN pool will not carry it.

What is P2WSH and why does the 100-Key Vault use it?

Pay-to-witness-script-hash, the SegWit output type (BIP-141, 2017) that commits to a spending script by its SHA-256 hash. The script is revealed only when the coins are spent, so until then the chain sees no public keys at all. Bitcoin Core relays P2WSH scripts up to 3,600 bytes with up to 100 witness items, which is exactly what makes a 100-key script possible. See the script in section 3.

What is SLH-DSA?

The stateless hash-based digital signature scheme NIST standardised in August 2024 as FIPS 205, derived from SPHINCS+. Its security rests only on hash functions, which no known quantum algorithm breaks in useful time. In the 100-Key Vault it is the off-chain approval that must exist before the keys will sign, so the decision to spend cannot be forged by a quantum computer even though the on-chain signatures still use ECDSA.

What is a one-time address, and why does it matter?

An address that receives coins once and spends them once, so its public key is revealed only in the spending transaction and never again. Bitcoin has recommended this since 2010 for privacy; for quantum security it is what keeps coins at rest invisible to an attacker. The 100-Key Vault enforces it by construction: the change from every spend goes into a fresh address with fresh keys. See section 3.

Does it work with existing HSMs?

Yes. The HSMs generate 100 secp256k1 keys through their ordinary key-generation call and sign through their ordinary signing call; no firmware change. The hash-based approval layer runs in software around the HSMs, not inside them, and the keys are deleted after signing through the standard destroy call.

Can an individual use One-Time Vaulting, or is it only for banks?

An individual can. The construction is a script, a never-reuse rule and a hash-based approval; nothing requires a hardware security module or a committee. At 20 keys it uses Bitcoin's ordinary multisig opcode and any wallet software that can build a custom witness script; the approval can be one hash-based key on a token you hold. 100 keys is the reserve-grade setting a custodian would run, and our open-source reference implementation runs it from one 24-word phrase on an ordinary computer. The discipline, not the number, is the method.

Is a hardware wallet quantum safe?

At rest, if you never reuse an address and do not use Taproot: a fresh hashed address shows the chain only a hash, whatever device holds the key. In flight, no: a hardware wallet reveals one public key when it spends, and a fast quantum machine would have about a 41% chance of beating the next block. Hardware wallets cannot run this method today without weakening it: they sign custom scripts only through registered wallet policies built on an exported xpub, and a quantum computer turns one exposed xpub into every key below it. Until firmware derives hardened keys internally, use an offline computer. See the reference implementation's FAQ.

Can a quantum computer break SHA-256 or mine bitcoin faster?

Not in any useful way. Grover’s algorithm gives at most a square-root speedup on hash search, and the published estimate for finding a SHA-256 preimage that way is around 2¹⁶⁶ operations, which no foreseeable machine performs. Google’s 2026 paper also rebuts the idea that quantum computers threaten mining. The quantum threat to Bitcoin is to its signatures, not its hashes, which is exactly why a hash is what the 100-Key Vault shows the chain at rest. See section 3.

What does a 100-Key Vault spend cost?

About 2,800 virtual bytes for one input and two outputs (our one-output mainnet spend weighed 2,759): roughly $4.50 at 2 sat/vB, $22 at 10 sat/vB and $112 at 50 sat/vB, at $80,000 per bitcoin in late October 2026. Nothing is paid to anyone but the miner. A 20-key vault spend is about a quarter of that. See section 6.

How long does the 100-Key Vault hold against quantum computers?

Below one in a million per spend through about 2032, below 1% through about 2035, and not to be relied on from about 2038, on our synthesis of the published expert surveys and hardware roadmaps. Those are estimates, labelled as such and reviewed annually. The window is wider than Bitcoin's own post-quantum migration window, which is the point. See section 8.

Is Taproot quantum safe?

No. Taproot (bc1p) addresses place a public key directly in the output, so those coins can be attacked at rest the day a large enough quantum computer exists. Google's 2026 paper counts Taproot as fully exposed. Coins in Taproot addresses should be moved to fresh hashed addresses, or vaults, while no such machine exists. See section 1.

I never reused an address. Is my bitcoin safe from quantum computers?

At rest, yes: a fresh bc1q or legacy hashed address shows the chain only a hash. In flight, no: the moment you spend, your single public key is visible until the transaction confirms, and a first-generation fast quantum machine would have about a 41% chance of deriving it first. The 100-Key Vault keeps the at-rest property and replaces the single-key race with a 100-key one.

What is BIP-360?

Pay-to-Merkle-Root, a proposed new Bitcoin output type that removes Taproot's exposed key path. It was merged into the BIPs repository as a draft in February 2026. By its own text it defers post-quantum signature opcodes to a future proposal, so on its own it fixes at-rest exposure, not on-spend. A co-author has estimated about seven years from a decision to widespread migration. See section 2.

What is BIP-361?

“Post Quantum Migration and Legacy Signature Sunset”, a draft Bitcoin Improvement Proposal by Jameson Lopp and others, published April 2026. It proposes retiring quantum-vulnerable signatures on a schedule: no new sends to legacy outputs about three years after activation, legacy spends invalid about two years later. It depends on a post-quantum signature proposal that has not yet been written, and it is the source of the figure that more than 34% of bitcoin has an exposed public key.

What is QSB, StarkWare's quantum-safe Bitcoin transaction, and how does it compare?

A construction published in April 2026 that buries a hash-based one-time lock inside a legacy Bitcoin script, so the spend's security rests on hash second-preimage resistance rather than on the curve. In flight it is cryptographically stronger than a 100-Key Vault. It is not yet deployable by a custodian: each spend needs hours of GPU grinding, the transactions are non-standard and must be handed to a cooperating miner, fees cannot be bumped, and it depends on legacy script behaviour a future cleanup could remove. One mainnet transaction exists. See section 6.

Is Ethereum more or less exposed to quantum attack than Bitcoin?

Both use the same curve and the same kind of signature, so both are exposed. Ethereum accounts reveal their public key on first transaction and keep using the same address, so most active Ethereum accounts are exposed at rest the way reused Bitcoin addresses are. Ethereum can, however, verify a post-quantum signature inside a smart contract today, which Bitcoin cannot, so a post-quantum vault on Ethereum can be cryptographically complete in flight. That is a different piece.

What is the Bitcoin quantum migration timeline?

No activation date exists. BIP-360 is a draft; the post-quantum signature proposal it needs has not been written. A BIP-360 co-author's public estimate is roughly three years to activation and five more for 90% of the economy to migrate, about seven years in total from a start in 2026, which points to the mid-2030s.

Is there a ready implementation of the 100-Key Vault?

Yes, at two levels. An open-source reference implementation builds, signs and spends the 100-key script with Bitcoin Core, and made the mainnet spend in this piece. For custodian banks, EternaX Labs has built the rest as EternaX Bitcoin Vault: the signing orchestration split across independent nodes, the hash-based approval layer, the recovery design, and a security model a bank can file. It runs on unmodified Bitcoin and unmodified HSMs. Details on request at info@eternax.ai, not in this piece.

Can I run One-Time Vaulting without EternaX?

Yes. Everything in this piece is standard Bitcoin and standard signing-device operation, the script is printed above, and the open-source reference implementation builds and spends it. What EternaX supplies is the operating discipline around it: the split-signing orchestration, the hash-based approval layer, the recovery design, and a security model a bank can file. The method does not depend on us.

Does this protect bitcoin on Lightning?

No. Lightning channels keep public keys live for the life of the channel, so they are at-rest exposed by design. One-Time Vaulting is for holding and settling; operational liquidity is a separate problem.

Isn't the hash-based approval just a document, since Bitcoin never checks it?

On chain, yes: Bitcoin verifies the 100 ECDSA signatures and nothing else. Operationally, no: it is the condition every signing system checks before any key is asked to sign, split across independent parties so no single system can trigger a spend, and it is the only part of the spend decision a quantum computer cannot forge. It is governance, and we call it that.

What if a quantum computer appears tomorrow?

Coins in exposed addresses, Taproot, pay-to-public-key and reused addresses, would be at immediate risk and should already have been moved. Coins behind hashes or in vaults would be safe at rest and exposed only when spent. A 100-Key Vault spend would then be the difference between a coin flip and a hundred coin flips, and between having a migration plan and not having one.

Does insurance cover quantum theft of bitcoin?

Ask your insurer; most custody policies are silent on it or exclude it. What a 100-Key Vault gives an underwriter is a quantified exposure with a date rather than an unquantified one, which is the precondition for any conversation about cover.

11. Glossary and references

At-rest attack. Attacking a public key that is already visible, with unlimited time.
On-spend (in-flight) attack. Attacking a key revealed by a pending transaction, before it confirms.
CRQC. A cryptographically relevant quantum computer: large enough to run Shor's algorithm against real keys.
Fast-clock / slow-clock. Google's distinction between platforms that can run the in-flight race (superconducting, photonic, silicon) and those that cannot yet (ions, neutral atoms).
Primed machine. A quantum computer that has precomputed the key-independent half of Shor's algorithm and is waiting for a public key.
P2WSH. Pay-to-witness-script-hash: a SegWit address that commits to a script by its SHA-256 hash.
Taproot / P2TR. Bitcoin's 2021 output type; places a tweaked public key directly in the output.
Full-RBF. Bitcoin Core's policy, default since v28 and mandatory since v29, that any unconfirmed transaction can be replaced by a higher-fee conflict.
SLH-DSA. NIST's stateless hash-based signature standard (FIPS 205), derived from SPHINCS+.
BIP-360 / BIP-361. Draft proposals for a key-path-free output type and for a scheduled sunset of legacy signatures.
Work factor. The resources an attacker must spend, as opposed to a mathematical hardness bound.
100-Key Vault. A One-Time Vault with 100 keys in one input, the most Bitcoin Core's default policy relays; the instance this piece describes.
One-Time Vaulting. Holding bitcoin behind N fresh keys that all sign, used once, with spends approved by a hash-based signature: a quorum for an institution, a single key for an individual.
OTV(N). One-Time Vaulting with N keys per input; OTV(20) for operational wallets, OTV(100) for reserves.
Post-quantum secure. Protected by cryptography no known quantum algorithm breaks: here, SHA-256 commitments and SLH-DSA signatures, at rest.
